# MCU Timeline：AI 实现计划

> 状态：待执行；本文件只定义实施计划，不代表功能已经完成。
> 制定日期：2026-09-30（America/Chicago）
> 基线：main / 8724b6fedc7cec8a49e4e84732e790cc47130b1c
> 目标：最好用的中文 MCU 观看导航，帮助观众决定看什么、理解观看关系、记录进度，并避免意外剧透。
> 本计划中的“AI 实现”指由 AI 编程助手推进开发；第一版不需要在线大模型服务。

## 1. 产品决策

“最好”以核心任务的完成质量衡量，不以功能数量衡量：

1. 新观众能迅速选择一条适合的观看路线。
2. 已有观众能记录已看作品，并知道下一部是什么。
3. 查时间线的观众能分清官方事实、编辑推断和未知信息。
4. 默认浏览不会泄露结局、身份反转或彩蛋。

优先顺序：数据可信度 → 无剧透与中文搜索 → 观看进度 → 可解释的路线 → 多宇宙图谱 → 分享与持续维护。

首版范围：中文、电影/剧集季/特别篇、静态部署、本机保存进度。账号同步、社区、用户评分、在线 AI 聊天和扩展整个漫威漫画宇宙，放在有真实需求后评估。

保留当前红黑视觉语言。先调整阅读与操作体验，不做全面视觉重建。

## 2. 已确认的基线与问题

本计划基于仓库 README.md、index.html 及实际页面检查：

- 当前仓库仅有 README.md 和 index.html；数据、CSS、脚本在一个页面内。
- 当前包含 68 个作品条目，具备排序、搜索、阶段/传奇/宇宙/类型筛选和电影倒计时。
- CHRONO_ORDER 是人工排序，混合故事年代与观看建议；例如 1964 年的神奇四侠放在后段。
- 中文“钢铁侠”搜索返回 6 部；英文“Tony Stark”返回 9 部。搜索依赖简介文本与英文角色名称，缺少统一中文角色别名。
- 简介直接包含终局之战与洛基第二季结局等重要剧透。
- 说明与实际分类不一致：说明将死侍与金刚狼归为变种人宇宙，卡片实际显示分支。
- formatInUniverse 将未知年份与时间之外合并展示，无法表达两者差异。
- eraFor 使用数组排名边界划分年代组，容易随着条目调整出现标签与年份不一致。
- README 宣称存在 mcu_data.json，但基线仓库中没有该文件。
- 筛选状态仅在内存；没有作品详情地址、观看进度和路线。

未验证的内容：68 条数据逐项准确性、最新档期、手机实机体验、性能和完整无障碍表现。不得把这些写成已通过检查。

## 3. 实现架构：尽量减少不必要的迁移

### 推荐方案

第一轮沿用原生 HTML/CSS/JavaScript，拆出 ES modules 和独立 JSON。保持 GitHub Pages 部署，不引入数据库和运行时 AI API。68 个条目的筛选、关系与路线都能在客户端确定性完成。

建议目录（实施时创建，当前尚不存在）：

- index.html：页面结构、基础元信息与无脚本说明
- styles/：设计变量、布局、组件样式
- src/app.js：入口与页面协调
- src/data.js：数据加载及错误处理
- src/search.js：角色别名与作品搜索
- src/timeline.js：顺序、分组与关系
- src/routes.js：路线选择与剩余清单
- src/storage.js：本机观看进度、导入导出与迁移
- src/state.js：URL 状态与界面状态
- src/views/：作品、详情、路线等渲染模块
- data/works.json：唯一作品数据源
- data/characters.json：角色与别名
- data/universes.json：宇宙定义
- data/relations.json：故事及观看关系
- data/routes.json：编辑精选路线
- scripts/validate-data.mjs：结构与交叉引用校验
- tests/：排序、搜索、剧透、存储与路线关键测试
- docs/：数据口径、更新流程、验收记录
- .github/workflows/：校验与部署检查

不要为满足目录形式而拆出空模块；按实际责任拆分。使用相对资源地址，验证 GitHub Pages 的 /mcu-timeline/ 子路径。加载失败要有明确提示及重试入口。

如未来状态复杂度明显增加，再单独评估 TypeScript、构建工具或组件框架；不将迁移框架作为产品价值的前置条件。依赖版本及工具 API 在实施时查官方文档并固定版本。

### URL 与本机状态

- 第一轮采用 hash 路由，支持作品详情和路线直达，避免 GitHub Pages 深层路径刷新 404。
- 筛选/排序/搜索写入可分享 URL；打开或刷新后恢复状态，浏览器前进后退可用。
- 观看进度本机保存，不默认放进分享 URL。
- storage 必须有版本号、迁移逻辑、异常处理和导入导出。
- 明确告知“保存在此浏览器”；无账号时不声称跨设备同步。

## 4. 数据模型与可信度规则

每个作品保留稳定 id，既有 id 尽量沿用。推荐字段：

| 范畴 | 字段与要求 |
| --- | --- |
| 标识 | id、titleZh、titleEn、aliases；id 唯一 |
| 类型 | film / seriesSeason / special，避免以 episodes === 1 推断类型 |
| 发行 | releaseEvents，区分电影节首映、北美院线上映、平台上线；包含地区、日期及确定程度 |
| 状态 | announced / scheduled / partiallyReleased / released；状态需人工核实，不能只因日期过去自动判定已上线 |
| 阶段 | phase 可空；非官方归类必须注明，不强制所有延伸作品有 MCU 阶段 |
| 宇宙 | primaryUniverseId、visitedUniverseIds；宇宙与 TVA/虚空等场所分开建模 |
| 故事时间 | known / estimated / unknown / outsideTime / anthology；主线时段与闪回/彩蛋分别记录 |
| 角色 | characterIds；角色表保存中文名、英文名、称号、常用别名 |
| 文本 | spoilerFreeSynopsis、spoilerSections；身份与角色显示也可以带剧透等级 |
| 时长 | runtimeMinutes 或季总时长；未知可空，估计值明确标识 |
| 证据 | sources：URL、支持的字段、来源类型、核实日期；争议留说明 |
| 关系 | 前置背景、直接续作、发生先后、分支起点、跨宇宙访问分别建模 |

规则：

1. 上映顺序、故事时间顺序、推荐观看顺序是独立口径。
2. 故事顺序优先展示同一宇宙内的可比较关系；跨宇宙日期不暗示故事互相先后。
3. TVA 不是普通年代，年份未知也不等于时间之外；诗选作品不能假装只有一个时间点。
4. 官方确认、编辑推断、传闻三类信息分开。传闻不得进入确定档期或必看前置。
5. 作品整体顺序与彩蛋观看建议可以不同，不靠一个全局排序解决全部情况。
6. 来源必须支持对应字段，不能所有条目统一挂一个索引页冒充逐条核实。
7. 不确定则保留 null 和说明；AI 不得补造精确日期、剧情、集数、宇宙编号或来源。
8. 首轮迁移保持 68 个原有 id；发现错误可纠正，但必须留下变更依据。新增或删除条目另写说明。

## 5. 分阶段任务与验收

以下工作包按依赖执行，每包建议一个可单独审查的 PR。实施前刷新仓库状态并遵循当前 AGENTS.md（若存在）。计划文件的提交不代表后续代码已获自动发布授权。

### P0-A：建立可维护基线

任务：
- 从 index.html 提取数据、CSS 与脚本，保留现有样式和功能。
- 创建真实唯一数据源，修正 README 的数据说明。
- 加入数据校验：重复 id、非法日期、引用不存在、枚举不合法、顺序漏项/重复。
- 补最关键的行为测试，记录页面基线。

验收：
- 68 个原有 id 均保留；计数、搜索、筛选与倒计时仍可用。
- 在 GitHub Pages 子路径可加载所有资源，数据加载失败不会只显示空白。
- 页面没有因拆分出现新增控制台错误。
- 测试不依赖固定当前日期；时钟可注入。

### P0-B：纠正口径与无剧透

任务：
- 替换按数组排名分组的年代逻辑。
- 分离三种顺序，未知年代和时间之外单独展示。
- 核实高风险条目及分类矛盾；日期与发行事件分开。
- 重写全部作品的无剧透简介，敏感内容按块展开。
- 角色、来源说明与关系节点也执行剧透规则。

验收：
- 1964 年作品不再无说明地进入“2027”年代组。
- 宇宙筛选、作品卡片与口径说明一致。
- 默认 DOM、屏幕阅读器文本、搜索预览和分享摘要均不包含被隐藏的剧透正文。
- 明确显示“待核实/推测”，不伪装成官方时间。
- 隐藏剧透不使用仅模糊文字等仍可读取的方案。

### P1-A：中文搜索与观看进度

任务：
- 用角色 id 与别名表搜索，支持“钢铁侠 / 托尼 / Tony Stark”等对应同一角色。
- 作品状态：未看 / 在看 / 已看 / 想看；剧集先以季为单位。
- 加入已看过滤、进度概览、重置与导入导出。
- URL 保存筛选、排序和搜索；观看进度保存在本机。

验收：
- “钢铁侠”与“Tony Stark”角色检索得到相同角色关联作品集；简介命中可另行区分。
- 刷新后进度保留；损坏 JSON、禁用存储、配额失败有可理解的处理。
- 导入文件先校验再修改已有进度；未知作品 id 不导致崩溃。
- 清空进度要求确认，并提供导出或撤销方式。
- 分享筛选 URL 不意外包含个人观看记录。

### P1-B：精选路线与下一部

任务：
- 首批完成：新手上映路线、无限传奇主线、多元宇宙路线、洛基角色路线。
- 在来源足够时加入毁灭日补课路线，明确为编辑建议；不得声称知道未上映电影的全部必需背景。
- 每条路线给出适用人群、包含范围、总时长及选择理由。
- 扣除已看作品，显示剩余清单与下一部；可切换完整路线。
- 标明剧情前置、建议了解和可选扩展。

验收：
- 路线没有重复或不存在的作品；前置依赖没有环。
- 标记已看后下一部和剩余时长正确更新；可选作品不阻塞主线。
- 完成路线、全部未看、只看电影、缺失时长等情况均有正确展示。
- 时长不确定时显示已知时长及缺失说明，不给虚假的精确合计。
- 推荐原因不含超出当前剧透设置的内容。

### P2-A：详情页与手机体验

任务：
- 作品详情展示无剧透设定、时间口径、前置背景、后续作品与逐项来源。
- 点击角色进入其关联作品列表。
- 手机把主要入口设为“选路线 / 继续观看 / 查时间线”，高级筛选按需展开。
- 加入紧凑浏览模式、明确点击状态和可用的返回操作。
- 采用有使用依据的海报资产，配置缺图回退与延迟加载。

验收：
- 详情和路线 URL 可直接访问并刷新。
- 390px、768px、桌面视口无内容溢出；另进行至少一次手机实机检查。
- 键盘可完成主要操作；筛选按钮有 aria-pressed 等状态，触控区域以 44px 左右为目标。
- 倒计时不每秒触发屏幕阅读器播报；减少动态效果设置有效。
- 不添加只能悬停才能理解的关键操作。

### P2-B：多宇宙图谱（核心功能通过后实施）

任务：
- 先确定图谱的故事关系口径，再设计交互。
- 展示主宇宙、其他宇宙与时间之外的独立轨道。
- 连线明确区分故事事件、分支与跨宇宙访问；观看建议不混成故事因果。
- 第一批只做来源充分的节点与关系；逐步扩展。
- 桌面可放大/定位；手机保留列表作为完整可用入口。

验收：
- 点击节点能打开对应详情，筛选/定位后能返回。
- 有文字图例和可键盘操作的等价列表。
- 不强迫所有 68 部作品挤在同一个可视区域。
- 数据不足的关系不画成确定连线；剧透设置覆盖节点和连线。
- 5 位用户测试若显示图谱比列表更难完成任务，则优先修复或延后图谱。

### P3：分享、发现与维护

任务：
- 作品/路线分享链接与清晰页面标题。
- 为需要搜索收录的作品和路线生成静态详情页；hash 路由本身不视为完整 SEO 方案。
- 添加描述、规范地址、适当结构化数据、站点地图与项目说明。
- 建立数据更新日志、提交纠错入口与来源复核流程。
- 优化字体、海报与资源加载，避免先加入大量视觉资产再处理性能。

验收：
- 分享链接可在新浏览器打开正确内容，摘要无剧透。
- 页面元信息对应作品/路线，不全部沿用首页。
- 数据更新在 PR 中呈现结构化差异并通过校验。
- 在固定设备/网络条件下记录性能基线；以移动端 LCP ≤ 2.5s、CLS ≤ 0.1、INP ≤ 200ms 为体验目标，区分实验室检查与实际用户数据。

> 本次仅实施工作包 [填写编号]，遵循其验收标准。

### 数据研究与代码任务的边界

- AI 可提取资料、提出分类与写代码；事实变更仍需可核查证据。

- 自动检查来源变化最多生成待审查建议，不自动改写档期和剧情。
- 不在源代码或静态网站内加入 API 密钥。
- 故事顺序和推荐顺序采用人工维护、可解释的数据；不让在线模型每次随机生成不同路线。
- 不用任务数量、生成代码量或泛化的“AI 已检查”替代验收证据。

## 8. 发布与成功标准

每个工作包可独立回滚，不在同一个 PR 中同时重写数据、视觉、框架与部署。

首个有明显价值的版本 = P0-A + P0-B + P1-A + P1-B。图谱不阻塞这个版本发布。

上线前请 5 位目标用户执行：
1. 从首页选择适合第一次观看的路线。
2. 查询洛基相关作品和观看前置，不被意外剧透。
3. 标记已看作品，刷新后找到下一部。
4. 分享一条路线，让另一位用户打开。

初始验收目标：至少 4/5 用户无需口头帮助完成前三项；多数用户能在 30 秒内找到合适路线。小样本用于发现问题，不用于宣称市场验证。后续根据自愿反馈评估回访、路线使用与数据纠错频率，不先为收集指标添加复杂后台。

优先修复让用户失败或失去信任的问题，再增加新的入口和动效。
