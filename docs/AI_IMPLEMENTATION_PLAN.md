# MCU Timeline：AI 实现计划

> 状态：待执行；本文件只定义实施计划，不代表功能已经完成。
> 制定日期：2026-09-30（America/Chicago）
> 计划版本：1.2；修订日期：2026-09-30
> 本轮修订：明确全站无剧透/完整剧透双模式、单部展开、偏好保存、搜索与分享行为，并加入首版验收。
> 基线：main / 8724b6fedc7cec8a49e4e84732e790cc47130b1c
> 目标：最好用的中文 MCU 观看导航，帮助观众决定看什么、理解观看关系、记录进度，并避免意外剧透。
> 本计划中的“AI 实现”指由 AI 编程助手推进开发；第一版不需要在线大模型服务。

## 1. 产品决策

“最好”以核心任务的完成质量衡量，不以功能数量衡量：

1. 新观众能迅速选择一条适合的观看路线。
2. 已有观众能记录已看作品，并知道下一部是什么。
3. 查时间线的观众能分清官方事实、编辑推断和未知信息。
4. 默认浏览不会泄露结局、身份反转或彩蛋。

优先顺序：数据可信度 → 手机核心流程验证 → 无剧透与中文搜索 → 本机已看进度 → 一条精品路线 → 按反馈扩展。

### MVP 与后续版本的明确边界

| 首版必须有 | 后续按需求扩展 |
| --- | --- |
| 现有目录仍可查询；关键事实核实或明确标为未知 | 补充更多延伸宇宙及作品 |
| 无剧透/完整剧透切换、单部展开、中文角色别名、保留现有筛选 | 分集进度、按观看进度自动解锁剧透 |
| 未看/已看、本机保存、隐藏已看、进度导出与安全恢复 | 在看/想看、账号、跨设备同步 |
| 一条“第一次看：无限传奇电影上映路线” | 多元宇宙、洛基、毁灭日等编辑路线 |
| 路线理由、下一部、可分享的路线地址 | 完整详情页、角色页、海报系统、SEO |
| 可用的手机首页与键盘操作 | 多宇宙图谱、复杂动效、社区及在线 AI |

首版路线包含官方无限传奇电影范围，按区域明确的原始上映顺序排列，逐项核实清单。只使用有证据的无剧透理由；不以“精简必看”名义做未经解释的删减。它首先验证观看闭环，之后再做省时路线。

第一版不同时做四条路线，不新增所有作品的完整详情页，也不一次性引入完整故事关系图。日期、宇宙等争议可以保持未知；剧透检查与 MVP 路线成员校验不能省略。

保留当前红黑视觉语言。先调整阅读与操作体验，不做全面视觉重建。

### 剧透模式：首版完整交互设计

全站支持两种模式，默认无剧透；此设置属于 MVP，不留到后续版本。完整剧透指展示项目已核实收录的剧情与彩蛋内容，不代表涵盖每个细节，也不将传闻升级为事实。

| 内容 | 无剧透 | 完整剧透 |
| --- | --- | --- |
| 卡片简介 | 基本设定与开场背景 | 剧情摘要，结局可在明确标识的扩展区展示 |
| 角色与身份 | 非惊喜角色及公开设定 | 揭晓身份、惊喜登场与变体关系 |
| 时间与宇宙 | 无剧透口径；敏感结论用中性占位 | 有依据的详细时间、分支和跨宇宙说明 |
| 彩蛋与关系 | 中性观看提醒 | 已核实彩蛋内容及其关联解释 |
| 搜索 | 只索引/展示安全文本和安全关联 | 可搜索已核实剧透文本与敏感关联 |
| 路线 | 无剧透理由和下一部 | 可额外展示剧情衔接理由，不改变路线成员及已看状态 |
| 图谱（后续） | 安全节点与关系；敏感项隐藏或中性化 | 展示已收录的敏感节点与连线 |
| 分享与元信息 | 始终使用无剧透标题、摘要与预览 | 分享预览仍然无剧透，不继承发送者的完整模式 |

#### 入口和切换

- 桌面和手机均在主工具区提供清晰的“无剧透 / 完整剧透”双选控件；显示当前选择，并提供可读状态。它不占用“开始/继续观看”的主要按钮位置。
- 首次切到完整剧透，显示一次简短提醒：“将显示已上映作品的结局、身份反转和彩蛋。”按钮为“开启完整剧透”和“取消”；确认前保持无剧透。
- 保存 spoilerMode 与提示已确认状态到此浏览器；再次主动切换不反复弹窗。损坏或未知设置回退无剧透。
- 后续访问恢复有效的已确认偏好。初始化先解析偏好，再渲染内容，避免剧透闪现。存储不可用时只在本次页面生命周期内保留选择，并说明无法记住。
- 从完整模式切回无剧透立即生效，清除所有单部展开与敏感搜索结果，不清空查询词、观看进度或筛选；查询若仅命中剧透则改为安全空结果。
- 模式切换不重置路线、已看标记、排序和滚动锚点；若当前焦点所在内容被移除，将焦点移到相应安全标题或控件。
- 无剧透表示隐藏敏感剧情，不表示内容一定适合所有年龄；不额外引入年龄确认。

#### 单部展开与状态优先级

- 无剧透模式下每部可点击“展开本作剧透”，旁边标明“含结局与彩蛋”。再点击可收起。
- 单部展开只影响本作的剧透区和本作敏感字段，不开启全站模式，不解锁别部内容或全局搜索/图谱。
- 如果某段内容同时泄露其他作品，用相关作品 id 标记；单部展开只显示所有关联作品均已显式展开的内容，其余提示“涉及其他作品剧透，切换完整模式查看”。
- 单部展开仅保存于当前页面会话内存，刷新回到全站偏好；全站模式每次改变均清除单部展开。
- “已看”只是观看记录，MVP 不自动解锁剧透；是否已看也不改变模式选择。
- 单部展开不需重复确认弹窗，明确按钮文字即告知影响；完整模式中不显示无意义的“展开剧透”控制，但长文本可以按阅读需要折叠。
- 缺少已核实的完整摘要时显示“详细剧情待补充”，保留安全简介；不能让 AI 为填满完整模式编造剧情。

#### 数据、搜索与渲染

- 统一使用 safe / spoiler 可见性标签；剧情段落、角色关联、关系边、时间说明、来源标签和推荐理由均执行同一策略。
- 敏感块携带 spoilerWorkIds，至少包含本作 id；跨作品内容列全关联作品。无标签的敏感内容视为审核失败。
- 剧透策略集中在独立模块中，过滤后再渲染。被隐藏文本不能仅靠 CSS 模糊或 display:none 留在 DOM、工具提示、aria-label、图片 alt 或预加载详情中。
- 安全搜索不能通过敏感别名、简介或角色关联命中作品，以免结果本身泄露身份与登场。当前“钢铁侠/Tony Stark 一致”验收在同一模式的可见关联集合内成立。
- 用户主动输入敏感查询词时不自动复述剧情，不建议含剧透的补全词。单部展开不改变安全搜索索引。
- 不将当前模式、单部展开或确认状态写入分享 URL。URL 无权自动开启剧透；新浏览器默认无剧透，已有浏览器遵循收件人自己的有效偏好。
- 公共 HTML 元信息、搜索引擎结构化数据、分享预览和静态预渲染正文一律无剧透；完整内容只在显式有效的模式下渲染。
- 外部来源可能剧透，以中性标签展示并提示；此站不能控制第三方页面内容。

#### 必须通过的模式测试

1. 新浏览器首次访问无剧透；取消首次提醒不改变状态；确认后开启并记住。
2. 刷新恢复偏好；损坏/未知设置回退安全，存储失败不崩溃。
3. 单部展开不影响其他卡片、搜索或图谱；刷新收起；跨作品敏感段不被单部误解锁。
4. 完整切回无剧透后，敏感 DOM、辅助文本与搜索结果立即消失，观看状态保留。
5. 同一搜索词在两种模式下按可见字段得到合理结果，不泄露安全模式隐藏的关联。
6. 分享链接在新浏览器不带入发送者的模式，预览无剧透；收件人自己的偏好不被链接覆盖。
7. 切换可通过键盘操作，选中状态可读，首次提醒焦点正确进入/返回；布局在手机可用。
8. 双模式均不把未核实剧情、传闻或尚未知内容展示为确认事实。

## 2. 已确认的基线与问题

本计划基于仓库 README.md、index.html 及实际页面检查：

- 审查基线的应用文件仅有 README.md 和 index.html；数据、CSS、脚本在一个页面内。此后已加入本计划文件；实施时须重新检查当前仓库。
- 当前包含 68 个作品条目，具备排序、搜索、阶段/传奇/宇宙/类型筛选和电影倒计时。
- CHRONO_ORDER 是人工排序，混合故事年代与观看建议；例如 1964 年的神奇四侠放在后段。
- 中文“钢铁侠”搜索返回 6 部；英文“Tony Stark”返回 9 部。搜索依赖简介文本与英文角色名称，缺少统一中文角色别名。
- 简介直接包含终局之战与洛基第二季结局等重要剧透。
- 说明与实际分类不一致：说明将死侍与金刚狼归为变种人宇宙，卡片实际显示分支。
- formatInUniverse 将未知年份与时间之外合并展示，无法表达两者差异。
- eraFor 使用数组排名边界划分年代组，容易随着条目调整出现标签与年份不一致。
- README 宣称存在 mcu_data.json，但基线仓库中没有该文件。
- 筛选状态仅在内存；没有作品详情地址、观看进度和路线。

未验证的内容：68 条数据逐项准确性、最新档期、手机实机体验、性能和完整无障碍表现。不得把这些写成已通过检查。

## 3. 实现架构：尽量减少不必要的迁移

### 推荐方案

第一轮沿用原生 HTML/CSS/JavaScript，拆出 ES modules 和独立 JSON。保持 GitHub Pages 部署，不引入数据库和运行时 AI API。68 个条目的筛选、关系与路线都能在客户端确定性完成。

建议目录（实施时创建，当前尚不存在）：

- index.html：页面结构、基础元信息与无脚本说明
- styles/：设计变量、布局、组件样式
- src/app.js：入口与页面协调
- src/data.js：数据加载及错误处理
- src/search.js：角色别名与作品搜索
- src/timeline.js：顺序、分组与关系
- src/routes.js：路线选择与剩余清单
- src/storage.js：本机观看进度、导入导出与迁移
- src/state.js：URL 状态与界面状态
- src/views/：作品、详情、路线等渲染模块
- data/works.json：唯一作品数据源
- data/characters.json：角色与别名
- data/universes.json：宇宙定义
- data/relations.json：后续阶段的故事及观看关系；MVP 不要求完整图谱
- data/routes.json：编辑精选路线
- scripts/validate-data.mjs：结构与交叉引用校验
- tests/：排序、搜索、剧透、存储与路线关键测试
- docs/：数据口径、更新流程、验收记录
- .github/workflows/：校验与部署检查

不要为满足目录形式而拆出空模块；按实际责任拆分。使用相对资源地址，验证 GitHub Pages 的 /mcu-timeline/ 子路径。加载失败要有明确提示及重试入口。

如未来状态复杂度明显增加，再单独评估 TypeScript、构建工具或组件框架；不将迁移框架作为产品价值的前置条件。依赖版本及工具 API 在实施时查官方文档并固定版本。

### URL 与本机状态

- 第一轮采用 hash 路由，支持作品详情和路线直达，避免 GitHub Pages 深层路径刷新 404。
- 筛选/排序/搜索写入可分享 URL；打开或刷新后恢复状态，浏览器前进后退可用。
- 观看进度本机保存，不默认放进分享 URL。
- storage 必须有版本号、迁移策略、异常处理和进度导出/安全恢复；无历史版本时不写无用途的迁移。
- 明确告知“保存在此浏览器”；无账号时不声称跨设备同步。

## 4. 数据模型与可信度规则

每个作品保留稳定 id，既有 id 尽量沿用。推荐字段：

| 范畴 | 字段与要求 |
| --- | --- |
| 标识 | id、titleZh、titleEn、aliases；id 唯一 |
| 类型 | film / seriesSeason / special，避免以 episodes === 1 推断类型 |
| 发行 | releaseEvents，区分电影节首映、北美院线上映、平台上线；包含地区、日期及确定程度 |
| 状态 | announced / scheduled / partiallyReleased / released；状态需人工核实，不能只因日期过去自动判定已上线 |
| 阶段 | phase 可空；非官方归类必须注明，不强制所有延伸作品有 MCU 阶段 |
| 宇宙 | primaryUniverseId、visitedUniverseIds；宇宙与 TVA/虚空等场所分开建模 |
| 故事时间 | known / estimated / unknown / outsideTime / anthology；主线时段与闪回/彩蛋分别记录 |
| 角色 | characterIds；角色表保存中文名、英文名、称号、常用别名 |
| 文本 | spoilerFreeSynopsis、spoilerSections；敏感字段统一 safe/spoiler 标记，敏感块携带 spoilerWorkIds 以控制跨作品泄露 |
| 时长 | runtimeMinutes 或季总时长；未知可空，估计值明确标识 |
| 证据 | sources：URL、支持的字段、来源类型、核实日期；争议留说明 |
| 关系 | 前置背景、直接续作、发生先后、分支起点、跨宇宙访问分别建模 |

规则：

1. 上映顺序、故事时间顺序、推荐观看顺序是独立口径。
2. 故事顺序优先展示同一宇宙内的可比较关系；跨宇宙日期不暗示故事互相先后。
3. TVA 不是普通年代，年份未知也不等于时间之外；诗选作品不能假装只有一个时间点。
4. 官方确认、编辑推断、传闻三类信息分开。传闻不得进入确定档期或必看前置。
5. 作品整体顺序与彩蛋观看建议可以不同，不靠一个全局排序解决全部情况。
6. 来源必须支持对应字段，不能所有条目统一挂一个索引页冒充逐条核实。
7. 不确定则保留 null 和说明；AI 不得补造精确日期、剧情、集数、宇宙编号或来源。
8. 首轮迁移保持 68 个原有 id；发现错误可纠正，但必须留下变更依据。新增或删除条目另写说明。

## 5. 分阶段任务与验收

以下工作包按依赖执行，每包建议一个可单独审查的 PR。实施前刷新仓库状态并遵循当前 AGENTS.md（若存在）。计划文件的提交不代表后续代码已获自动发布授权。

### P0-A：建立可维护基线

任务：
- 从 index.html 提取数据、CSS 与脚本，保留现有样式和功能。
- 创建真实唯一数据源，修正 README 的数据说明。
- 加入数据校验：重复 id、非法日期、引用不存在、枚举不合法、顺序漏项/重复。
- 补最关键的行为测试，记录页面基线。

验收：
- 68 个原有 id 均保留；计数、搜索、筛选与倒计时仍可用。
- 在 GitHub Pages 子路径可加载所有资源，数据加载失败不会只显示空白。
- 页面没有因拆分出现新增控制台错误。
- 测试不依赖固定当前日期；时钟可注入。

### P0-B：纠正口径与无剧透

任务：
- 替换按数组排名分组的年代逻辑。
- 分离三种顺序，未知年代和时间之外单独展示。
- 核实高风险条目及分类矛盾；日期与发行事件分开。
- 重写全部作品的无剧透简介，敏感内容按块展开。
- 角色、来源说明与关系节点也执行剧透规则。
- 实施第 1 节双模式设计：全站切换、首次提醒、有效偏好保存和单部展开；明确存储不可用时的回退。
- 使用集中式剧透策略，先过滤再渲染，安全搜索仅索引安全字段。

验收：
- 1964 年作品不再无说明地进入“2027”年代组。
- 宇宙筛选、作品卡片与口径说明一致。
- 默认 DOM、屏幕阅读器文本、搜索预览和分享摘要均不包含被隐藏的剧透正文。
- 明确显示“待核实/推测”，不伪装成官方时间。
- 隐藏剧透不使用仅模糊文字等仍可读取的方案。
- 第 1 节的八项模式测试通过；两种模式均覆盖卡片与当前搜索功能，详情/图谱随各自阶段继续执行同一策略。

### P0-C：先验证手机首页与核心流程

任务：
- 用低成本可操作原型比较首页入口，不先实现整套视觉重设计。
- 默认候选：首次访问显示“开始无限传奇路线”为主要操作，“查时间线”为次要操作；选择路线后，“继续观看”成为主要操作。
- 以已保存的活动路线为依据展示继续观看；仅有零散已看标记时不擅自推断用户正在看哪条路线。
- 减少首屏倒计时与筛选的占用，高级筛选按需展开；保留原有查询入口。
- 验证：开始路线 → 标记已看 → 刷新 → 继续下一部，以及查找指定作品。
- 记录不同用户任务的误点击与困惑，确定布局后再做完整实现。
- 原型加入双模式入口，验证开启、取消、切回及单部展开，不让剧透控件抢占核心观看入口。

验收：
- 390px 手机视口中主要操作清晰，不需要先理解“阶段/传奇/连续性”才能开始。
- 路线已完成、未选择路线、只有零散已看、存储不可用时都有合理入口。
- 原型标明真实功能与模拟内容，不将模拟持久化宣称为完成。
- 有用户参与时记录实际结果；没有参与者时可继续工程实现，但“用户验证”保持未验证，不伪造数据。

### P1-A：中文搜索与观看进度

任务：
- 用角色 id 与别名表搜索，支持“钢铁侠 / 托尼 / Tony Stark”等对应同一角色。
- MVP 仅做未看/已看；剧集以季为单位，在看/想看和分集进度暂缓。
- 加入已看过滤、轻量进度概览、导出/安全恢复及重置。
- URL 保存筛选、排序和搜索；观看进度保存在本机。

验收：
- “钢铁侠”与“Tony Stark”在同一剧透模式中检索得到相同的可见角色关联作品集；简介命中可另行区分。敏感关联不能借别名绕过隐藏规则。
- 刷新后进度保留；损坏 JSON、禁用存储、配额失败有可理解的处理。
- 导入文件先校验再修改已有进度；未知作品 id 不导致崩溃。
- 清空进度要求确认，并提供导出或撤销方式。
- 分享筛选 URL 不意外包含个人观看记录。

### P1-B：精选路线与下一部

任务：
- MVP 仅完成“第一次看：无限传奇电影上映路线”，保持一个清晰、可核查的范围。
- 后续通过扩展条件再增加多元宇宙、洛基及省时路线。
- 毁灭日路线仅在来源足够时加入，明确为编辑建议；不得声称知道未上映电影的全部必需背景。
- 每条路线给出适用人群、包含范围、总时长及选择理由。
- 扣除已看作品，显示剩余清单与下一部；可切换完整路线。
- MVP 提供无剧透的路线说明及作品入选理由；完整前置依赖与可选扩展留待后续路线阶段，避免先建设全量关系图。

验收：
- 路线成员与核实清单一致，没有重复或不存在的作品；后续若加入前置依赖，其依赖不得有环。
- 标记已看后下一部和剩余时长正确更新；可选作品不阻塞主线。
- 完成路线、全部未看、部分已看、缺失时长等情况均有正确展示；MVP 本身为电影路线，不新增无用途的路线类型切换。
- 时长不确定时显示已知时长及缺失说明，不给虚假的精确合计。
- 推荐原因不含超出当前剧透设置的内容。

### P2-A：详情页与手机体验

任务：
- 作品详情展示无剧透设定、时间口径、前置背景、后续作品与逐项来源。
- 点击角色进入其关联作品列表。
- 在已通过 P0-C 并随 MVP 实现的手机入口上继续打磨；本阶段不承担首次修复手机核心流程的工作。
- 加入紧凑浏览模式、明确点击状态和可用的返回操作。
- 采用有使用依据的海报资产，配置缺图回退与延迟加载。

验收：
- 详情和路线 URL 可直接访问并刷新。
- 390px、768px、桌面视口无内容溢出；另进行至少一次手机实机检查。
- 键盘可完成主要操作；筛选按钮有 aria-pressed 等状态，触控区域以 44px 左右为目标。
- 倒计时不每秒触发屏幕阅读器播报；减少动态效果设置有效。
- 不添加只能悬停才能理解的关键操作。

### P2-B：多宇宙图谱（默认暂缓，满足条件才启动）

启动条件：以下四项全部满足，并在执行记录中列出证据：
1. MVP 的开始路线、保存已看和继续观看流程已通过功能验收。
2. 至少 3 位真实目标用户独立反馈需要理解分支/跨宇宙关系，记录问题原话与任务，不以开发者兴趣代替需求。
3. 一个小规模图谱原型与现有文字/列表比较，能帮助用户完成具体关系题且没有额外剧透；记录完成情况及困惑，不从小样本推导统计显著结论。
4. 首批展示关系有逐条依据、确定程度和无剧透显示策略。

没有用户或关系证据时保持暂缓；可以改进文字解释与列表，图谱不进入 MVP 发布依赖，也不强制占首页。

任务：
- 先确定图谱的故事关系口径，再设计交互。
- 展示主宇宙、其他宇宙与时间之外的独立轨道。
- 连线明确区分故事事件、分支与跨宇宙访问；观看建议不混成故事因果。
- 第一批只做来源充分的节点与关系；逐步扩展。
- 桌面可放大/定位；手机保留列表作为完整可用入口。

验收：
- 点击节点能打开对应详情，筛选/定位后能返回。
- 有文字图例和可键盘操作的等价列表。
- 不强迫所有 68 部作品挤在同一个可视区域。
- 数据不足的关系不画成确定连线；剧透设置覆盖节点和连线。
- 5 位用户测试若显示图谱比列表更难完成任务，则优先修复或延后图谱。

### P3：分享、发现与维护

任务：
- 作品/路线分享链接与清晰页面标题。
- 为需要搜索收录的作品和路线生成静态详情页；hash 路由本身不视为完整 SEO 方案。
- 添加描述、规范地址、适当结构化数据、站点地图与项目说明。
- 建立数据更新日志、提交纠错入口与来源复核流程。
- 优化字体、海报与资源加载，避免先加入大量视觉资产再处理性能。

验收：
- 分享链接可在新浏览器打开正确内容，摘要无剧透。
- 页面元信息对应作品/路线，不全部沿用首页。
- 数据更新在 PR 中呈现结构化差异并通过校验。
- 在固定设备/网络条件下记录性能基线；以移动端 LCP ≤ 2.5s、CLS ≤ 0.1、INP ≤ 200ms 为体验目标，区分实验室检查与实际用户数据。

## 6. AI 编程助手工作协议

### 每次任务的输入

提供本计划、当前仓库状态、要完成的工作包、明确不包含的工作，以及相关来源或视觉参考。先读代码和已有约束，再确定改动。

### 每次任务的输出

1. 完成一个范围明确的工作包。
2. 运行与改动相关的数据校验和行为测试。
3. UI 变更实际打开页面验证，报告桌面/手机检查范围。
4. 提供变更说明、验证结果、剩余问题与回滚方式。
5. 更新本文件中的执行记录，写真实状态，不把计划当完成结果。

### 推荐执行提示词

> 阅读 docs/AI_IMPLEMENTATION_PLAN.md 和仓库现有说明，刷新当前分支状态。
> 本次仅实施工作包 [填写编号]，遵循其验收标准。
> 保留既有作品 id、红黑视觉和 GitHub Pages 子路径兼容性。
> 不编造 MCU 数据，不顺手加入账号、数据库、AI API 或其他工作包。
> 如来源不足，用待核实标记并说明缺口。
> 完成必要校验和实际页面验证，提交一个可审查的 PR，说明变更、证据、测试与限制。
> 不自动合并或部署，除非当前用户指令已经明确授权。
> 报告完成情况并更新执行记录。

### 数据研究与代码任务的边界

- AI 可提取资料、提出分类与写代码；事实变更仍需可核查证据。
- 使用官方 Marvel/Disney 等第一手资料优先；冲突写明来源日期与口径。
- 自动检查来源变化最多生成待审查建议，不自动改写档期和剧情。
- 不在源代码或静态网站内加入 API 密钥。
- 故事顺序和推荐顺序采用人工维护、可解释的数据；不让在线模型每次随机生成不同路线。
- 不用任务数量、生成代码量或泛化的“AI 已检查”替代验收证据。

## 8. 数据审核与资源预算

### 独立的数据审核清单

实施 P0-A 时创建 docs/DATA_AUDIT.md（或同等结构化文件），一行对应一个现有作品 id，至少包含：

| 审核项 | 记录要求 |
| --- | --- |
| 收录与类型 | 是否属于本目录范围，电影/季/特别篇；官方阶段或延伸作品 |
| 发行与状态 | 发行事件、区域、日期、是否真实上线，来源与核实日期 |
| 宇宙与时间 | 主宇宙/访问地点，主线年代、确定程度、争议与支持证据 |
| 角色与别名 | 中文/英文关联完整；惊喜身份是否会泄露 |
| 无剧透内容 | 简介、角色、标题附注、理由、来源展示文本逐项检查 |
| 路线与时长 | 是否属于 MVP 路线；顺序来源；时长已知/估计/缺失 |
| 处理结果 | 已核实 / 明确未知 / 待审 / 有冲突；不得只写“AI 检查通过” |

按优先级分批审核：
- 第一批：MVP 路线的全部成员、已发现的分类矛盾、待上映作品的档期与状态。
- 第二批：其余目录的发行状态、无剧透文本与显著矛盾。
- 第三批：其余目录的精确年代、完整角色、时长及更细关系。

MVP 发布要求：路线成员范围与顺序全部核实；所有可见文本完成剧透检查；高风险发行与分类问题解决或显式标成未知。其余条目未核实的具体字段暂不作为确定事实展示。审核覆盖率与事实正确率不是同一指标。

sources 不得泄露被隐藏的结局标题；如来源标题本身剧透，默认显示中性标签，访问前提示可能包含剧透。静态 JSON 可含后续剧透，本项目保护的是正常浏览体验，不承诺阻止主动查看源文件。

### 先估工作量，再承诺时间

- 先审核 5 个代表条目：早期电影、剧集、跨宇宙作品、时间之外、待上映作品。
- 记录查源、冲突处理、无剧透编辑所花时间，再估剩余 63 条工作量。
- 数据研究和编码分别估算；不以 AI 写代码速度推断资料核实速度。
- 工作包以完成验收为准，不承诺固定 4–6 周全部完成。
- 每完成一包只细化下一包；图谱和 SEO 在启动前不做大规模预实现。
- 找不到可靠资料时记录缺口，保留未知，避免重复搜索耗尽预算；关键路线依据不足则暂停该路线发布，其他独立任务继续。

## 9. 发布、反馈与启动条件

每个工作包可独立回滚，不在同一个 PR 中同时重写数据、视觉、框架与部署。

首个有明显价值的版本 = P0-A + P0-B + P0-C + P1-A + P1-B 的 MVP 范围。手机核心流程、数据校验和剧透保护必须在这一版完成；完整详情、海报、其他路线、图谱和 SEO 不阻塞首版。

实施顺序：P0-A → P0-B → P0-C → P1-A → P1-B → MVP 功能验收与用户反馈 → 选择一个后续方向。

发布前确认 Pages 当前发布来源（分支直发或 workflow），不能假设推送 main 不会触发上线。文档可按用户请求提交；应用变更先在工作分支/PR 中验证，并依据当次指令决定合并或发布。保留部署前版本与可恢复的进度格式，说明回滚步骤。

上线前请 5 位目标用户执行：
1. 从首页选择适合第一次观看的路线。
2. 查询洛基相关作品及时间口径，不被意外剧透；完整前置推荐留待后续路线。
3. 标记已看作品，刷新后找到下一部。
4. 分享一条路线，让另一位用户打开。

初始验收目标：至少 4/5 用户无需口头帮助完成前三项；多数用户能在 30 秒内找到合适路线。小样本用于发现问题，不用于宣称市场验证。后续根据自愿反馈评估回访、路线使用与数据纠错频率，不先为收集指标添加复杂后台。

无法取得真实参与者时，交付可测试的 MVP 并列明人工验证待办；不伪造 4/5 通过或把 AI 模拟用户当真人。工程验收与用户验证分别记录，避免外部测试长期阻塞独立修复。

### 每轮只选一个扩展方向

| 反馈证据 | 下一步 |
| --- | --- |
| 用户找不到开始或下一部 | 修首页和观看流程，暂停加功能 |
| 用户频繁指出年代/状态问题 | 补数据审核和口径解释 |
| 至少 3 位用户需要某一具体补课目标 | 先做该目标的一条编辑路线，核实其依赖与理由 |
| 用户希望逐部查来源与关联 | 做 P2-A 完整详情 |
| 符合 P2-B 的四项条件 | 启动小规模图谱 |
| 主要困难是分享或搜索发现 | 做 P3 对应部分 |

每轮记录“已学到什么、仍未知什么、下一步为何值得做”。路线不因开了数据模型就自动扩展，图谱可以长期不做。

优先修复让用户失败或失去信任的问题，再增加新的入口和动效。
